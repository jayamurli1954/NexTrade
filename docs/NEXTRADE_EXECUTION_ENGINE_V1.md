# NexTrade Sub-Phase 3F — Controlled Execution Subsystem & Engine Orchestrator

## Executive Summary
Sub-Phase 3F implements the **Execution Engine Orchestrator** (`execution/engine.py`) and contracts (`contracts/execution.py`). It unifies the sub-components established throughout Phase 3 into a single non-bypassable execution control system:

```text
RiskEngine -> ExecutionGateway -> BrokerAdapter -> ProtectionLifecycleManager -> ReconciliationEngine
```

---

## Architectural Invariants (E34 — E41)

### 1. Invariant E34 — Controlled Gateway Entry Single Point
- Entry orders must originate from authorized `RiskDecision` payloads passing through `ExecutionGateway`.
- Protection exit executions require `ProtectionDecision` and retain parent `RiskDecision` and signal lineage.

### 2. Invariant E35 — No Broker Bypass for Protection Exits
- All protection exit requests generated by `ProtectionLifecycleManager` pass through `ExecutionGateway` -> `BrokerAdapter`.
- Direct broker calls from protection managers are strictly prohibited.

### 3. Invariant E36 — Authoritative State Machine Synchronization
- `ExecutionStateMachine` is authoritative for tracking order lifecycle states (`CREATED` -> `AUTHORIZED` -> `SUBMITTED` -> `FILLED`/`PARTIALLY_FILLED`/`REJECTED`/`UNKNOWN`).
- `ExecutionEngine` coordinates state transitions across all requests.

### 4. Invariant E37 / E39-NonRetry — Automatic UNKNOWN Escalation & Non-Retry
- Orders resulting in `ExecutionStatus.UNKNOWN` automatically register with `ReconciliationEngine`.
- Automatic retries of `UNKNOWN` orders are prohibited without formal reconciliation resolution.

### 5. Invariant E38 — Subsystem Restart State Serialization
- `ExecutionEngine.to_dict()` and `from_dict()` serialize state machines, position IDs, open quantities, protected quantities, protection lifecycle states, trailing stop states, pending UNKNOWN queues, reconciliation keys, idempotency keys, generation counters, and lineage IDs.
- Subsystem recovery guarantees zero duplicate exit submissions on restart.

### 6. Invariant E39 — Execution Lineage Preservation
- Every execution request retains complete lineage tracing: `execution_request_id`, `risk_decision_id`, `signal_id`, `position_id`, `parent_execution_request_id`, `protection_trigger_reason`, `generation`, and `idempotency_key`.

### 7. Invariant E40 — Position Quantity Conservation
- Enforces \( Q_{\text{open}} = Q_{\text{entry\_filled}} - Q_{\text{exit\_filled\_cumulative}} \).
- Enforces \( 0 \le Q_{\text{protected}} \le Q_{\text{open}} \).

### 8. Invariant E41 — Single Active Protection Manager per Position
- Ensures `position_id` maps to exactly 0 or 1 active `ProtectionLifecycleManager`.
- Multi-order fills or scale-in submissions consolidate into the existing active position manager rather than creating duplicate managers.
